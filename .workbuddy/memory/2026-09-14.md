## 接入腾讯云 CloudBase AI 网关

- 目标：把用户自己的 CloudBase AI 网关配成编码助手的模型服务商（OpenAI 兼容）。
- 环境 ID：`alic-pc-d6gtkv3xt8f5229ac`
- Base URL：`https://<ENV_ID>.api.tcloudbasegateway.com/v1/ai/cloudbase`（`cloudbase` 是资源点套餐的统一 provider）
- **可用模型只有 `hy3`（混元3）**；deepseek-v3/r1、kimi-k2、glm-4.5、qwen3、hunyuan-* 全部未开通。要加模型需到 控制台 → AI → 生文模型 开启。
- 流式验证通过：标准 OpenAI SSE，`data: {"choices":[{"delta":{"content":"..."}}]}`。

### 排障要点（下次直接用）
- CloudBase AI 网关**没有 `GET /models` 接口**，请求它会被当成「名为 models 的模型」而返回 403。
- 用错误码区分故障源，这是最快的判定法：
  - `401 INVALID_CREDENTIALS` → 密钥无效/已吊销
  - `403 AI_MODEL_NOT_SUPPORTED` → 密钥有效，但模型未在控制台开通
  - 拿一个假 key 打同一接口做对照组，能一次性区分这两者。
- 官方文档自相矛盾：`openai-sdk-access` 页示例写 `deepseek-v4-flash`，但 `quickstart/ai-tools` 页写 `hy3`。实测以控制台实际开通的为准。

### 产出
- `scripts/cloudbase-ai-probe.cjs`：探测可用模型 + 输出编码助手配置。密钥只从 `CLOUDBASE_ENV_ID` / `CLOUDBASE_API_KEY` 环境变量读，不落仓库。
- npm script: `check:cloudbase`

### 安全提醒（已告知用户）
- 用户贴出的 API Key 是 `role: service_role` + `is_system_admin: true` + 永不过期，等同环境 root 权限，已建议吊销重签。
- 该项目是纯前端 Vite 应用，`VITE_*` 会被打进 `dist/assets/*.js`，此类管理员密钥**绝不能**走前端环境变量。
